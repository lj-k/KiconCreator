# deepseek深度思考

总体评价：架构文档覆盖度较高，模块拆分、状态机、引用计数、导出矩阵等关键点基本成型。但对照《需求文档 V2.02》，仍存在一批**需求遗漏**、**架构内部/与需求矛盾**、以及**可行性风险**。以下按这三类给出评审意见，重点放在架构层必须澄清或补落位的问题。

---

## 一、需求遗漏点

### 1. 响应式与竖屏/手机布局细节缺失
需求三.2 明确：
- 默认视口 800×400，以上无滑块，随视口变大展开更多参数；
- 小于默认视口可产生纵向滑块，但预览固定显示；
- 竖屏时预览固定浮动在视口上方，最大高度不超过视口 1/3；
- 手机横排进入三栏模式；
- 纵向结构下所有标签组均合并；
- 标签组按模块内可用高度做“平分法拆解”，并有“反压模块高度→反压栏高度→栏内滚动”的级联链路。

架构 `ui.js` 只写了 `observeResponsive()` 和级联压缩原则，缺少上述断点、竖屏浮动、最大高度、横排三栏、所有标签组合并等具体约束。架构层应补充响应式状态机或断点表。

### 2. 多行排版模式未完整枚举
需求二.1.2 对 1~9 行分别列出排版模式：
- 1 行：上半边、下半边、左半边、右半边、居中；
- 2 行：全在上、全在下、全在左、全在右、左右分、上下分；
- 3 行：一字横排、一字纵排、品字、倒品；
- 4 行：一字横排、一字纵排、四宫格、纵向 121、横向 121；
- 5~9 行各有具体模式。

架构 `layouts.js` 只列了 `single/pair/triple/quad/multi/ring/grid` 函数，未给出完整枚举与 `arrangement` 值映射。架构层应补一张“行数→可选 arrangement 枚举→布局函数”的映射表，否则实现时容易漏模式。

### 3. 多行排列层次命名与枚举不完整
需求二.1.3 有两个选项：
- 「1 行‑>9 行」：绘制顺序 `9→8→…→1`，行 1 最后绘制，最顶层；
- 「9 行‑>1 行」：绘制顺序 `1→2→…→9`，行 9 最后绘制，最顶层。

架构 schema 只写 `layerOrder: "9-to-1"`，并注释“9-to-1 = 绘制顺序 9→8→…→1，行1 最顶层”。命名与需求选项名称容易混淆，且未列出另一个枚举值。应改为需求原义的两个枚举，例如 `draw9to1` / `draw1to9`，并明确与 UI 选项文案的映射。

### 4. 快速复制样式缺少架构落位
需求二.2.9 要求内容标签内容最顶部有两个按钮：复制样式、粘贴样式，复制字段集合为尺寸、颜色、阴影，排除内容参数；跨模式只应用交集。

架构“需求分析总览”提到了快速复制样式，但核心模块设计中没有对应模块、接口、UI 落位、字段交集算法。应在 `ui.js` 或独立 `styleClipboard.js` 中定义：
- 复制字段路径集合；
- 跨模式交集规则；
- 粘贴时是否进 undo 快照；
- 与参数联动的交互。

### 5. FA 搜索缺少“关键词”字段
需求二.2.7：搜索支持别名、关键词。架构 `fa_map.js` 只有 `unicode / aliases / category / pathData`，没有 `keywords`。应补充 `keywords` 字段，否则无法满足关键词搜索。

### 6. FA 版权提示未落位
需求二.2.7：FA 标签内增加 FA6 商用版权提醒；页面最底部增加一行简短 FA6 版权提示。架构 `fa_map.js` 和 `fonts.js` 未提 UI 落位。应在 `ui.js` 或 `fa_map.js` 中明确提示文案、显示位置、触发条件。

### 7. 文本输入框行为未明确
需求二.2.4：文本模式输入框不限制字符串长度，强制居中，超出可左右滚动。架构 `createLineTabTitle` 只提“文本输入框”，未写不限制长度、居中、横向滚动。架构层应补充该特殊组件的交互约束。

### 8. 图片上传进度条与失败原因提示缺失
需求二.2.8：上传图片显示进度条，大于 1MB 提醒卡顿；上传失败提示包含原因。架构 `images.upload()` 只写 `FileReader.readAsDataURL → 校验大小`，未提进度条、失败原因 UI。应在 `images.js` 或 `ui.js` 中补上传状态机。

### 9. 样式标签级重置按钮缺失
需求二.3.3：各标签下显示重置按钮。架构 `createRangeParam` 有 `onReset`，但这是参数级重置；标签级重置（如整个“尺寸”标签重置）未明确。应区分参数重置与标签重置。

### 10. 背景布局比例的多滑块/均分 UI 未落位
需求三.2.3：
- 层间比例：多滑块共享滑轨，多个输入框，均分按钮；
- 层内比例：多滑块共享滑轨，多个输入框，均分按钮；
- 方向：饼图多层时多滑块共享滑轨，层数=滑块数量。

架构 schema 有 `layerRatios`、`ratios`、`directions`，但 UI 层未定义“共享滑轨多滑块”组件。且 `ratios` 是扁平数组，多层每层独立分界线时，结构可能不足以表达“按层分配”。应明确数据结构，例如 `ratios: number[][]` 或 `ratiosByLayer`。

### 11. 填充边界参数联动/重置 UI 未落位
需求三.2.3：边界参数 A、ω、φ、k 有滑块、值显示兼输入框、联动、重置。架构 `LINKABLE_PARAMS` 包含 `background.boundary.params.*`，但 UI 未明确这些参数如何显示联动链条图标和重置按钮。

### 12. 顶部工具栏缺少标题/作者
需求四.1：显示标题、作者（Kong）。架构顶部工具栏只提撤销/重做、联动按钮、主题切换，未提作者。应补 UI 落位。

### 13. 预设导入差异展示、加载失败提示未明确
需求二.2.1：导入后显示具体差异参数情况；如果一条参数也没有成功加载则显示加载失败；批量导入显示成功/差异/失败数量及名称。架构 `Presets.import` 返回 `success/warnings/failures`，但未定义 UI 如何展示差异参数、加载失败提示。架构层应明确返回结构与 UI 呈现的契约。

### 14. 历史右键/长按删除交互未明确
需求二.2.2：右键或长按显示删除按钮。架构 `History.delete(id)` 只有接口，未定义触发交互与 UI 状态。

### 15. 主题选择按钮位置未明确
需求三.1：标题后面界面样式选择按钮。架构主题系统只定义 CSS 变量和 `setTheme`，未提按钮位置。

### 16. 标签启用状态显示不完整
需求三.3：
- 形状非无时，形状标签上显示形状；
- 阴影和边框启用时，标签上显示绿色对号。
架构 `createToggleParam` 有 `showGreenCheck`，但“形状标签显示形状”未落位。

### 17. 参数联动范围可能遗漏
需求二.3.7：所有参数设置，每个参数后面加联动图标。架构 `links` 只列了部分样式参数，`color.gradientType`、`fontSize`、`weight`、`italic`、`textLayout`、字体、图片、FA 等内容参数均未出现在 `links` 或 `LINKABLE_PARAMS`。至少 `color.gradientType` 属于样式参数，明显遗漏。架构应明确“可联动参数白名单”，并说明内容参数是否参与联动。

### 18. 新增行联动继承逻辑过宽
需求二.3.7：如果有参数被勾选联动，新增行也同时联动。架构 `setLineCount` 中只要“任意行有任意 links=true”，新行所有可联动参数 `links` 全部设为 true。这会导致新行所有参数都联动，而不是只继承已勾选的那些参数。应改为：对每个参数，若已有行该参数 `links=true`，则新行该参数 `links=true`。

### 19. 行数减少时图片引用处理矛盾
需求二.3.3：行被减去增加后其参数和模式不必重置；需求二.2.8：切换行和模式不解除引用。架构 `images.js` 却写“行删除（content.lineCount 减少，该行 enabled=false 并移除）→ deref 该行 imageIds”。如果行数减少就 deref，重新增加行时 imageId 仍在 state 中，但 ImageRepo 可能已释放，图片丢失。应改为：行数减少仅 `enabled=false`，不 deref；只有真正更换图片、删除预设/历史、快照淘汰时才 deref。

### 20. 会话图片仓库 ref/deref 未与 state.set 自动绑定
需求六.1：所有引用图片仓库的参数变动都应注销或增加其引用。架构 `ImageRepo` 定义了引用来源，但 `state.set` 中未自动处理 `imageId` 变更时的 `deref` 旧 / `ref` 新。若依赖 UI 层手动调用，极易漏。架构层应明确：`state.set` 检测到 `*.imageId` 路径时，自动走 ImageRepo 引用迁移。

## 二、内部矛盾点

### 1. 主题 `theme` 是否进快照矛盾
架构 schema 中 `theme: "bright"` 属于业务 State，且“十七、快照 Schema 边界”写 undo/redo 快照包含 `theme`。但“十五、UI 视图状态 vs 业务 State 隔离”表格中又把“主题选择”列为 UI 视图状态，不进 undo 快照、不导出预设/历史。两处矛盾。需明确主题是否属于业务状态。

### 2. 填充方向旋转中心与需求原文矛盾
需求三.2.3 原文：“旋转的中心点为内容/图片/图标的中心。”架构第十四节歧义确认 1 说“经确认，旋转中心 = 形状中心（画布中心）”，并称需求原文为笔误。但需求文档中没有该确认记录。若没有需求方书面确认，架构单方面改为中心会与需求文档冲突。应标记为待确认，不能直接作为定论。

### 3. 颜色建议一键填充仅纯色 vs 架构支持渐变
需求三.2.4：“一键填充仅限制纯色。”架构 `colors.js` 注释却写：“单色一键填充：直接设置 fills[i].mode='solid'... 渐变填充：设置 fills[i].mode='gradient'...”。矛盾。应删除渐变一键填充，或明确渐变建议只作为颜色选择器的候选项，不直接切换 mode。

### 4. `layerOrder` 命名与需求选项语义易反
需求「1 行‑>9 行」对应绘制顺序 `9→8→…→1`，行 1 最顶层；架构 `layerOrder: "9-to-1"` 字面像“从 9 到 1 绘制”，但需求选项名是“1 行->9 行”。命名与 UI 文案映射不清，容易实现反。应改为需求原义枚举。

### 5. `makeName` 中 FA 代号内部不一致
架构歧义确认 4 说 FA 使用 `iconName`（如 `heart`），但 `Export.makeName` 注释写“FA 模式 → faMap[faIcon].unicode 或 iconName（FA 代号）”。应统一为 `iconName`，删除 unicode 备选。

### 6. `background.layout.ratios` 结构与需求多层独立比例不匹配
需求三.2.3：层内比例按层分配，每层色块数 -1 个分界线。饼图 2 层、每层 3 色时，需要每层 2 个分界线，共 4 个，且分属不同层。架构 schema 只给 `ratios: [0.5, 0.5]` 扁平数组，未表达“按层分组”。应改为 `ratios: number[][]` 或 `layerRatios` 与 `ratiosByLayer` 分离。

### 7. `render.js` 中 `ctx.clip(block)` 笔误
架构渲染流水线写 `ctx.clip(block)`，但 `block` 是对象，应为 `ctx.clip(block.clipPath)`。这是小笔误，但架构文档应修正以免实现误解。

### 8. `buildExportCanvas` 与 `render` 设置尺寸可能冲突
`buildExportCanvas(state, size)` 先设 `c.width = c.height = size`，但 `Renderer.render(c, state, { mode:'export' })` 内部又设 `canvas.width/height = state.canvas.size`。若 `size` 与 `state.canvas.size` 不一致，会互相覆盖。应明确导出尺寸就是 `state.canvas.size`，或让 render 接受尺寸参数。

### 9. `FA_CATEGORIES` 用 `filter` 过滤对象
架构 `fa_map.js` 中：
```js
const FA_CATEGORIES = {
  'Solid': FA_MAP_ALL.filter(k => k.category === 'solid'),
  ...
};
```
`FA_MAP_ALL` 是对象，不是数组，`filter` 不可用。应为 `Object.values(FA_MAP_ALL).filter(...)`。小错误，但架构文档应修正。

## 三、可行性不高 / 风险点

### 1. `fa_map.js` 本地打包全部 FA6 Free 图标 + pathData 体积过大
需求要求本地打包 FontAwesome6 全部图标，支持分类、搜索、别名、关键词，并直接绘制。架构方案是 `fa_map.js` 含 `unicode / aliases / category / pathData`。FontAwesome 6 Free 有 2000+ 图标，每个 `pathData` 可能几百到几千字节，整个文件可能达数 MB。普通 `<script>` 按序加载会阻塞主线程，且“主界面加载后异步加载”与“普通 script 按序加载”存在矛盾。建议：
- 拆分为多个分包，按分类懒加载；
- 或只存 unicode + 字体文件，放弃 pathData，用 `fillText` 渲染；
- 或使用 IndexedDB（但需求禁止 localStorage，未禁止 IndexedDB，但为保持零持久化可不用）。
这是架构层可行性风险，需要重新评估。

### 2. 普通 script 按序加载大量模块，依赖顺序脆弱
架构为了 `file://` 兼容，放弃 ES modules，改用普通 `<script>` 按序加载。目录中有 18 个 JS 文件，依赖关系图复杂。普通 script 按序加载要求 HTML 中脚本顺序严格正确，否则运行时报错。架构层应给出明确的加载顺序清单，或引入一个极简的命名空间/注册器来降低耦合。

### 3. 边框向外延伸的 Canvas 实现不可靠
需求要求边框从形状边框向外延伸。架构风险点已提：`Path2D.offset` 浏览器支持差，fallback 用 `stroke` 线宽内外各半，视觉上只有一半向外。若要求严格向外，可能需要手写路径偏移算法。架构层应选定策略，并评估对复杂多边形/角星路径的偏移是否会产生自交。

### 4. 饼图多层 + 每层独立方向 + 层内比例多滑块交互复杂
需求三.2.3 要求饼图布局层数≥2 时每层独立方向，层内比例每层独立分界线，多滑块共享滑轨。架构 `fillers.split()` 注释笼统，`directions[]` 和 `ratios` 结构未完全展开。实现时涉及极坐标分割、角度累加、层间半径、每层旋转，且要保证“任意参数下颜色填满整个形状”。这是高复杂度点，架构层应补充几何模型和数据结构。

### 5. 参数联动批量改写可能触发大量重渲染
顶部工具栏“全部联动/全部不联动”会改写所有行所有可联动参数，并同步链条图标。若每改一个参数都触发 `state:changed` 和重渲染，可能卡顿。架构应明确批量变更使用 `batchSet` + 一次 `pushUndo` + 一次 `render`，并防抖 UI 更新。

### 6. 图片引用计数场景多，容易不对称
架构风险清单已提，但实际有 6+ 场景：行图片、背景填充图片、undo、redo、history、presets、预设导入替换、行数减少、模式切换、更换图片。任何一处漏 `deref` 会内存泄漏，漏 `ref` 会误释放。建议在架构层定义“引用变更唯一入口”，例如 `State.setImageId(path, newId)` 统一处理，而不是散落在 UI 和 images.js。

### 7. 全量 JSON 快照 + 动态上限仍可能内存压力
虽然快照不含 base64，但 state 含 9 行 × 6 填充 × 多层比例/方向数组，每条快照可能数 KB 到数十 KB。20 条通常可接受，但频繁拖动滑块后 mouseup 入栈，若防抖不当会快速累积。架构应明确入栈防抖策略、快照序列化字段白名单。

### 8. 双 CDN 全失效的本地兜底未在目录中体现
技术选型说 Tailwind 双 CDN + 本地部署同一份，但目录结构只有 `css/styles.css`，没有本地 Tailwind 预编译文件。若 CDN 全失效，本地兜底不存在。应补 `css/tailwind.min.css` 或说明 `styles.css` 包含最小兜底。

### 9. `navigator.deviceMemory` 兼容性有限
架构用 `navigator.deviceMemory` 决定 undo 栈上限。该 API 并非所有 Chrome/Edge 版本都支持，且可能返回 `undefined`。应提供 fallback 默认值（如 15 或 20），并在架构中注明。

### 10. 字体加载与 file:// 协议
需求要求 web 字体按需加载，失败回退并提示原因。`file://` 下加载远程字体可能因 CORS 或混合内容失败。架构有回退，但应明确：默认预加载字体是否本地打包？若依赖 CDN，file:// 下可能不可用。建议默认字体使用系统字体或本地打包小体积字体。

### 11. 大尺寸画布 + 多阴影 + 多 clip 性能
canvas.size 可达 8192，多行内容独立阴影、形状阴影、边框、多色块 clip、边界过渡，全部在 Canvas 2D 上实时渲染，可能卡顿。架构有 DPR 隔离和导出 1:1，但未提离屏 canvas 缓存、脏矩形、分层渲染。详细设计时需评估。

## 四、建议优先修正项（P0）

1. **补完整响应式断点表**：800×400、竖屏预览浮动 1/3、手机横排三栏、标签组合并/平分法。
2. **补 1~9 行排版模式完整枚举**，以及 `layerOrder` 双枚举。
3. **明确参数联动白名单**，至少补 `color.gradientType`，并说明内容参数是否联动。
4. **修正新增行联动继承逻辑**：按参数继承，而非全部参数。
5. **修正行数减少图片引用策略**：不 deref，保留引用。
6. **统一主题是否进快照**，消除第十五节与 schema/快照边界矛盾。
7. **明确填充方向旋转中心**，若需求方未确认，不能直接改为形状中心。
8. **修正颜色建议一键填充仅纯色**，删除渐变一键填充。
9. **补快速复制样式模块落位**。
10. **补 FA 关键词字段与版权提示落位**。

二、内部矛盾点（架构自己打架）
M1. theme 是否进撤销快照 —— 三处互相矛盾 🔴
§15 明确："UI 视图状态……主题选择……❌ 不进 undo 快照"
§17 却写："undo/redo 快照 包含：canvas, content…, theme, version"
需求（四）2："不产生动作历史：……界面样式"，主题属于界面样式，不应进快照。
结论：§17 有误，需删除 theme；否则主题切换会污染撤销栈，且按需求属于违规。
M2. 引用计数 ref/deref 次序前后矛盾 🔴
§6："undoStack 每条快照 → 入栈时 ref"
§9 undo()："current = undoStack.pop() → 对 current 的 imageIds 全部 ref()"
快照已在入栈时 +1，栈间转移时再 +1 即双重计数；redo 同理。更根本的问题是："当前活动 state"的引用从未被建模——图片上传时 add 记 refCount=1，此后入栈快照不断 ref，但没有任何地方定义"当前 state 那一份引用"在 undo 覆盖时由谁 deref。按现文档执行必然出现计数膨胀或提前释放。建议：明确"当前 state 占 1 份引用 + 每份快照各占 1 份"的总账模型，重写 §9 的转移伪代码。
M3. 行隐藏时 deref 图片，与"行恢复"矛盾 🔴
§4.11 引用规则："行删除（lineCount 减少，enabled=false）→ deref 该行 imageIds"
§4.2 setLineCount：重新启用行时"links 状态保留，重新增加时恢复"——图片不在恢复范围。
deref 后 5 秒图片即被释放，用户收起第 3 行再展开，该行图片已丢。与需求三 3.3"行被减去增加后其参数和模式不必重置"的精神冲突。建议：行隐藏仅解除 UI 显示、不 deref（state 中 imageId 持续占引用），deref 仅发生在真正的状态覆盖（如 undo 淘汰）。
M4. "拉伸不改变渐变效果"的注释方向写反 🟡
§4.7 写"先画渐变再 transform"。Canvas 中 transform 作用于其后的所有绘制，若渐变在未变换坐标系创建后再 scale，渐变必然随文本被拉伸——效果恰与目标相反。正确路径是：对渐变坐标做逆变换补偿，或"文本先离屏绘制（含渐变）→ 再整体拉伸贴回"。架构至少应把这句话改为"渐变坐标系需与拉伸解耦（策略见设计文档）"。
M5. 联动 UI 组件与联动参数范围不一致 🟡
§4.2 LINKABLE_PARAMS 包含布尔/枚举参数（clipToShape、shadow.enabled、color.mode 等），需求 3.7 也明确"布尔类型也要有联动"；但 §4.9 中只有 createRangeParam 带 onToggleLink，createToggleParam / createColorParam 均无联动链条图标入参。组件层覆盖不了注册表范围，实现时必然返工或漏做。
M6. 背景参数联动"注册了但没落地" 🟡
LINKABLE_PARAMS 扩展到了 background.fills.*.color、background.boundary.params.* 等路径，但 links 标记只存在于 line 对象上（_fillDef 无 links 字段），§4.2 的 toggleLink/set 也只按 content.lines.i.X 提取 subPath。背景联动的标记存储位置、同步逻辑完全悬空。架构自己说"由详细设计决定是否启用 UI"，但至少要定数据结构，否则 schema 不闭环。
M7. canvas.transparent 一个字段两种语义 🟡
schema 注释强调"语义：白色键控透明（不是'是否填白'）"，但渲染流水线 2a（shape=none）又把它当"背景是否透明"用；而 2b（有形状）分支没有任何白色键控的后处理步骤（无 getImageData/alpha=0 环节）。建议拆成两个正交概念或在流水线补一步显式的键控后处理，避免实现者各按一种理解做。
M8. 小项
§4.12 import："遍历所有 imageId → deref 旧 + ref 新"——导入是新列表项，无"旧"可 deref，系残留文字。
_lineDef/_fillDef/__initialized/presets_builtin 写在"完整数据模型" JSON 里却未标注"非 state 字段"，照此实现会混入快照与预设导出，污染数据。
阶段一验收含"参数联动勾选后值同步"，完整状态机却排在阶段二，验收项超前于交付物。

## 一、需求遗漏点（架构未覆盖或覆盖不全）
### 1. UI交互与组件类遗漏
1. **图片剪裁器交互能力缺失**
需求明确剪裁器需要支持：缩放、拖拽、**快速比例**（1:1、16:9、3:4等比例快捷按钮）。架构文档`images.js::openCropper`仅标注入参`initialCrop,onConfirm`，**架构层没有在模块契约上明确必须支持快速比例能力**，仅留函数占位，架构没有把该能力标记为必须能力，容易在后续详细设计遗漏。

2. **非法输入完整交互契约缺失**
需求：非法输入→输入框底色浅红，闪烁两次，回退到最近合法值。架构`ui.js::createRangeParam`只提到非法输入处理，但**架构层面没有定义该交互属于UI层契约，没有明确：滑块拖动不触发闪烁，仅直接输入非法值才触发闪烁**；容易出现拖动滑块也触发红色闪烁的bug。

3. **多栏模式「放大按钮」边界条件缺失**
需求：放大按钮仅**多栏模式下可用**，点击后左栏变为视口50%宽度。
架构`preview.js::expandPreview()`只写了动作，**没有架构约束：单栏/纵向手机布局下放大按钮必须隐藏不可用**；架构没有约束该按钮的显示条件，属于需求能力遗漏。

4. **预设列表UI约束架构层未固化**
需求：预设列表仅展示预览缩略图，**不显示名称、不显示删除按钮，点击缩略图直接应用预设；缩略图尺寸严格小于50px屏幕像素，后加载不阻塞主界面**。
> 现状：架构`presets.js::renderList`描述了一部分，但**没有架构契约约束：禁止渲染删除按钮、禁止显示预设名称**；仅在注释描述，架构层没有作为模块约束，后续详细设计容易额外加上名称/删除按钮，违背需求。

5. **下载历史交互细节缺失**
需求下载历史：右键**或长按**唤起删除按钮（PC鼠标右键，移动端长按）。架构`history.js`只写`delete(id)`接口，**架构没有明确模块需要同时支持鼠标右键事件 + 移动端长按两套触发机制**。

6. **字体加载提示完整场景缺失**
需求：
- 下拉框中，未加载字体标注「未下载」；
- 加载中，预览图显示「字体加载中」提示；
- 加载失败回退字体并提示失败原因。
架构`fonts.js`提到上述点，但**没有架构约束：渲染导出的时候，字体还未加载完成如何处理导出结果**（例如导出是等待字体加载完成再导出，还是直接使用回退字体导出）。需求没有明说，但属于产品必须处理的边界，架构没有给出处理策略。

7. **FA版权提示两处位置，架构约束弱**
需求：FA模式标签内要有商用版权提醒，页面底部增加简短FA6版权提示。架构只在阶段四验收点提及，**没有在模块/数据模型层作为硬性契约约束，容易遗漏底部全局版权文本**。

### 2. 业务逻辑、边界场景遗漏
1. **ICO下载 + 多尺寸打包组合场景边界未定义**
需求：勾选多尺寸打包，下载ZIP；ICO下载不受导出尺寸设置影响。
现有下载矩阵描述了部分组合，**缺少场景：勾选多尺寸打包，同时单独点击ICO下载按钮；以及勾选多尺寸打包+勾选ICO下载，ZIP包内包含什么内容的完整契约**。虽然在表格写了一部分，但架构没有完整定义所有按钮的组合行为。

2. **预设批量导入的UI反馈信息架构缺失**
需求：批量导入预设，需要展示：成功、参数差异、失败预设数量+对应预设名称。架构`presets.import`返回`{success[],warnings[],failures[]}`，但是**架构没有约束UI层必须把差异参数、失败名称暴露给用户，仅定义返回数据结构**；架构文档作为架构，应明确该返回结果必须透传到UI反馈。

3. **命名规则兜底策略不足**
需求：文件名：文本拼接，过滤非法字符，总长度截断。
架构十四歧义点补充：无文本时兜底为icon。
> 遗漏场景：**全部文本过滤之后变成空字符串（全部是非法字符）**，架构仅兜底“icon”，但没有架构约束：当截断之后为空、全部非法字符场景完整兜底逻辑；容易生成`KIcon--20260911.zip`这种中间段为空的文件名。

4. **透明色逻辑：shape=none + JPG组合边界**
需求：透明勾选代表白色转为透明，JPG不支持透明。
架构render流水线写了shape=none分支，但是缺少一个边界：**shape=none，勾选透明，导出JPG**，架构虽然提到JPG强制不透明，但架构契约没有把该组合作为强制校验场景。

5. **动作历史撤销重做：图片引用计数的边界场景遗漏**
需求：撤销栈、重做栈快照要做图片ref/deref。
架构描述了redo清空deref，undo/redo切换ref/deref。
> 遗漏场景：执行undo之后修改参数触发pushUndo，此时被丢弃的redo栈快照全部deref，架构`clearRedoWithDeref`描述了，但是**没有架构约束：当undo栈FIFO淘汰旧快照时，必须对淘汰快照内全部imageId执行deref**，架构仅在文字描述，没有在state.js模块契约中固化。

6. **会话图片仓库：动图处理边界约束弱**
需求：上传动图取首帧。`images.js::upload`提到动图取首帧，**架构没有定义：如果动图解析失败（损坏GIF）的错误处理策略：报错提示、拒绝加入ImageRepo**。

### 3. 响应式与标签组自适应的需求缺口
需求：标签组分为「唯一标签组、并行标签组」；并行标签组空间充足自动平铺，不足自动堆叠；唯一标签组不能平铺拆分；采用平分法拆解标签。
> 现状：架构`ui.js::createTabGroup`有参数`parallel`。
> 遗漏：**架构没有定义模块契约：唯一标签组无论视口空间多大禁止平铺展开**；仅注释说明，没有架构强制约束，后续实现容易把唯一标签组错误做平铺。

### 4. JSON Schema与导入导出需求遗漏
需求：预设导入：JSON多出参数抛弃，缺失参数填充默认值。
架构`presets.import`描述逻辑，但**架构没有定义：导入预设JSON版本字段校验策略：文档写“不做版本校验”，但是没有定义高版本预设json导入低版本程序时，如何处理新增的未知字段，只说抛弃多余参数，缺少对未来向前兼容策略的描述**。

## 二、架构文档内部矛盾 / 和需求冲突点
> 重点：架构文档和需求文档语义冲突，架构内部模块之间互相冲突。

1. **填充layout.directions旋转中心（已识别歧义，但架构文档存在两处描述不一致）**
> 需求原文笔误：“旋转的中心点为内容/图片/图标的中心”，架构十四确认修正为**形状/画布中心**。
> 矛盾：架构文档多处地方：
> - 4.1 schema注释写`pie type + layers≥2 → 每层独立方向；旋转中心 = 形状中心（画布中心）`（正确）
> - 但在`fillers.js`注释还残留旧描述，架构文档文本没有全部清理干净，会造成阅读歧义。

2. **参数联动注册表范围的矛盾风险（高风险）**
架构`LINKABLE_PARAMS`注册表把大量背景参数加入联动（`background.fills.*.color`、边界参数等）。
> ⚠️**需求文档：参数联动仅针对【内容参数栏各行参数】，需求没有要求背景色块、边界参数支持参数联动链条UI**。
> 架构层面做了扩展：架构定义注册表支持背景参数联动，但是又备注“UI是否显示链条图标由详细设计决定”。
> 矛盾点：
> 1）架构数据模型已经把背景参数加入可联动注册表，业务state中预留大量links能力，但是**原始需求没有该功能，属于架构超范围设计；如果后续不实现UI，这些字段会一直存在JSON schema，预设导入导出、undo快照都会序列化这些无用字段，JSON体积膨胀，预设文件产生多余字段**。
> 2）如果后续详细设计忘记“UI不实现背景联动”，开发会额外实现需求之外的背景参数联动，超出需求范围。
> 建议：架构层区分：**预留扩展注册表和需求必实现注册表，把背景相关联动参数标记为P2扩展，不在V2.02版本schema中启用，V2.02只实现content.lines.*的参数联动**。

3. **预设导出图片剪裁量化的契约矛盾（高风险）**
需求：预设导出的时候，将图片**剪裁量化，只保存可见部分图片数据**。
架构`presets.js::export`：对图片做剪裁量化，存入JSON。
> 冲突点：
> 用户导出预设json，保存到本地；后续导入预设，只能得到剪裁之后的图片，原始大图丢失。
> 需求文档只写导出时候剪裁量化，**没有定义导入行为的用户提示**；架构文档风险描述5提到这点，但是：架构没有定义UI必须提示用户“导出预设中的图片已经剪裁，不再包含原图”。
> 同时：下载历史、撤销重做快照只存imageId引用，不存base64；而预设导出JSON携带剪裁后的base64，两者存储模型不一致，架构文档需要明确区分三类快照（undo、history、preset导出）存储模型差异，目前分散在各个章节，没有集中汇总。

4. **line数组常驻模型和需求的一致性校验**
需求：切换行数，减少行的时候，参数、模式、联动状态不重置，重新增加行数恢复状态。
架构模型：固定9个line常驻数组，通过`enabled`字段开关，不push/pop。
> ✔该模型符合需求。
> 内部小矛盾：架构`setLineCount`函数注释：“从未初始化过，按DEFAULT_LINE初始化”，这里有边界：当lineCount从9降到1，再回到9，所有行对象保留，符合需求；但是架构没有写清楚：行对象不会被销毁，只是enabled=false。文档部分注释容易误导阅读者。

5. **边界参数tan函数处理的两处描述不一致**
schema约束：`background.boundary.params.ω ∈0.01~10`，禁止ω=0；
而`fillers.boundary`描述：`ω=0返回直线fallback`。
> 矛盾：schema已经限制最小0.01，运行时理论不会出现ω=0，但是渲染层依然写了fallback逻辑。
> 属于双重保护本身没问题，但架构文档需要说明：**schema是输入层校验；渲染层是兜底防护，防止外部导入预设JSON非法绕过schema校验传入ω=0**。当前文档没有说明两层防护各自的目的，阅读容易混淆。

6. **撤销重做快照与session字段**
架构说明：undo快照不序列化`session.*`；session.images是轻量索引，完整图片放在ImageRepo。
> 内部冲突点：架构schema JSON模型中`session`放在顶层state对象，但是undo快照序列化的时候排除session；但是preset导入导出逻辑中，preset JSON**不包含session字段**。架构文档要明确：`session`是页面运行时内存状态，**永远不写入预设导出JSON**，目前描述分散，没有集中强调。

## 三、可行性不高 / 性能风险点（架构层面，非代码实现bug）
> 评估：在纯浏览器、无后端、不使用localStorage，全部内存运行约束下，架构方案的可行性。

1. **预设批量导入，携带多张base64图片，内存暴涨风险（高风险）**
> 架构：预设导出JSON会携带剪裁量化后base64图片；批量导入预设，图片全部解码注册进ImageRepo内存。
> 场景：用户导入一个外部批量预设json，里面包含几十张base64图片。全部驻留在内存，刷新页面释放。
> 约束：需求规定不能使用localStorage，全部内存。
> 风险：浏览器内存持续上涨，页面卡顿甚至OOM崩溃。
> 当前架构防护：只有refCount为0延迟5s释放。
> 架构层面缺失防护策略：**架构没有定义导入预设最大数量限制，没有定义单预设图片大小上限**；仅靠UI提示“图片大于1MB卡顿”，针对导入预设没有限制。

2. **8192大画布尺寸 + DPR预览风险，架构已有识别但防护策略不足**
架构风险清单第8点识别：canvas.size最大8192；预览canvas和导出canvas解耦。
> 风险：虽然导出canvas强制1x，但是预览交互、模态预览器，模态查看器需要1:1真实尺寸预览（需求：模态查看器按下载设置真实尺寸1:1显示）。
> 当canvas=8192，模态查看器创建8192×8192的canvas，浏览器很多版本上限是16384像素，8192本身接近上限，多张大图片叠加极易触发浏览器分配失败，canvas变黑/渲染失败。
> ⚠️架构文档：仅提到预览canvas做容器尺寸缩放；**没有架构策略约束模态查看器：当真实尺寸超过浏览器canvas最大支持尺寸时做降级（缩放预览并提示用户）**。架构没有定义降级策略，只依赖浏览器原生能力，可行性存在隐患。

3. **全量JSON快照撤销重做性能风险**
架构：undo/redo每一次都是完整state全量快照，state固定包含9行line、6个fill对象。即使用户仅仅修改一个滑块参数，也要深度clone整个大state对象。
> 虽然单份快照体积不大（<5KB），但是高频拖动、快速切换参数，短时间大量生成全量快照，会带来GC压力。
> 架构当前方案：V2版本选择全量快照（简化状态管理，符合浏览器工具），**但架构文档没有写明：明确放弃增量快照方案，选择全量快照的取舍理由**。后续维护人员不知道当初为什么不做增量diff快照。

4. **Tailwind CSS双CDN兜底方案可行性疑问**
技术选型：Tailwind使用CDN，同时有最小本地兜底。
> 架构描述“最小本地兜底”，但是没有架构定义：什么叫最小本地兜底，是预编译的完整css，还是只包含基础布局的精简子集；如果CDN失效，本地兜底是否能完整支持三栏、响应式、标签组全部UI组件。如果本地兜底是精简子集，UI会错乱，架构文档需要明确兜底包的能力边界。

5. **FontAwesome 6 Free全部图标本地打包fa_map.js体积风险**
需求要求：本地打包FA全部图标数据，主界面加载后异步加载。
> FA6 Free全部图标带pathData、category、aliases，JSON/js文件体积会很大（预估几百KB级别）。
> 架构：主界面初始化之后异步加载fa_map.js。该策略可行。
> 但是架构文档没有定义：**当fa_map.js加载失败（网络问题）的降级策略：FA模式禁用，UI提示，隐藏FA相关控件**。现在只描述成功加载流程，缺少失败降级契约。

## 四、架构文档自身的缺陷（文档本身，非设计缺陷）
1. 部分需求约束仅放在注释、阶段验收点，**没有上升到模块契约、数据模型约束**；架构文档应当把需求强制约束固化在模块定义，而不是散落注释和测试验收点。例如预设列表禁止显示名称、删除按钮。
2. 多处存在需求早期草稿残留文本（例如填充旋转中心旧描述），文档内部文本不一致，容易误导阅读者。
3. 三类快照（undo快照、download history快照、preset导出JSON）存储模型差异，分散在各个章节，缺少一张汇总对比表，方便阅读者快速理解。
4. 风险清单中，部分风险只描述风险，没有写清楚：**P0必须解决 / P1后续迭代**的优先级标记。
5. 歧义确认章节，部分歧义没有写清楚“V2版本最终的行为是什么”，只写确认逻辑。

## 六、总体结论
1. 整体架构**模型选择合理**：纯浏览器无后端，采用全量状态快照 + ImageRepo引用计数管理图片资源，模块拆分清晰，数据模型基本对齐需求；已经识别大量歧义点和风险。
2. 主要问题集中：①**部分需求约束仅写在注释/验收点，没有固化成架构模块契约，详细设计阶段容易遗漏**；②架构做了超需求范围扩展（背景参数联动），会引入多余字段；③部分边界异常场景、降级策略缺失；④文档存在少量历史草稿残留文本，会造成阅读歧义。
3. 可行性层面：核心功能可行；主要风险来自**大量base64导入预设带来的浏览器内存OOM，以及超大画布模态预览器浏览器canvas上限问题**，需要补充架构层面防护策略。

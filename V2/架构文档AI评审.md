# deepseek深度思考
对《KiconCreator V2 架构设计文档》的评审意见

> 评审角度：架构模型、模块边界、内部一致性、与《需求文档.md》的匹配度。  
> 不深入代码细节，重点关注“谁负责什么、数据如何流动、边界是否清晰”。

---

## 一、总体评价

架构文档整体覆盖度很高，模块划分、渲染流水线、引用计数、撤销重做、响应式、导出矩阵等都已成体系，明显优于普通“功能清单式”设计。

但当前文档存在三类需要优先修正的问题：

1. **图片仓库 / 预设 / 历史 / 快照之间的引用模型边界不够清晰**，多处存在“存 base64 还是存 imageId”的混淆。
2. **部分模型结构不足以表达需求**，典型是“层内比例按层分配”和“填充方向旋转中心”。
3. **架构文档单方面“确认”了若干与需求原文冲突的事项**，但需求文档未同步更新，形成事实上的需求不匹配。

下面按“模型与模块边界问题”“内部矛盾”“需求不匹配/遗漏”三类展开。

---

## 二、模型与模块边界问题

### 1. 预设、历史、图片仓库的引用模型边界模糊

需求（六）1 明确：

> 加载预设后，预设列表中预设包含的图片数据被自动剥离加载注册到图片仓库，预设列表中预设包含的图片变更为引用。  
> 应有引用计数（图片参数、预设、历史下载、动作历史撤销栈都计数）。

架构中却出现矛盾：

- `Presets.export(state)` 返回含“剪裁量化后图片 base64”的 JSON。
- `Presets.saveCurrent(name)` 又说“等同于 export → push 到 `state.session.presets`”。
- 同时 `ImageRepo` 引用来源清单又写 `session.presets[k].imageIds → +1`。

这导致一个问题：**会话内的预设列表到底持有的是 base64，还是 imageId 引用？**

如果 `saveCurrent` 直接把 `export` 的 JSON push 进预设列表，那么预设列表就持有了 base64，与“预设列表中图片变更为引用”冲突，也会让 `ImageRepo.refCount` 失真。

建议明确区分两种形态：

- **交换格式**：导出/导入用的 JSON，含剪裁量化 base64。
- **会话内预设**：只存业务参数 + imageId 引用；图片数据统一在 ImageRepo。

`saveCurrent` 应走“剪裁量化 → 注册 ImageRepo → 预设只存 imageId”，而不是直接 push 含 base64 的 JSON。

---

### 2. `presets.import` 与 `presets.apply` 职责混淆

需求 2.1 区分了两个动作：

- **导入预设**：把外部 JSON 加入预设列表，显示缩略图，不一定要立即替换当前 state。
- **点击预设**：应用预设，使内容参数、背景参数、预览同步更新。

架构 `Presets.import` 中写：

> JSON.parse → 遍历所有 imageId → ImageRepo.deref 旧 + ref 新  
> 返回 success / warnings / failures

这里“deref 旧 + ref 新”更像“应用预设到当前 state”的行为，而不是“导入到预设列表”的行为。  
如果导入时直接 deref 当前 state 的旧图片，会破坏当前编辑现场。

建议拆分为：

- `importPresets(jsonText)`：只解析、校验、注册图片、加入预设列表。
- `applyPreset(presetId)`：替换当前 state，处理当前 state 与目标预设之间的图片引用转移。

---

### 3. `history.recover` 缺少图片引用转移规则

需求 2.2：

> 历史列表保存当前的数据 json，并根据数据 json 绘制预览图。  
> 对于上传图片的处理，历史列表中的图片是指向上传图片的 id 或引用，不直接保存图片数据。

架构 `History.record` 写了对快照内 imageIds 调用 `ImageRepo.ref`，这是对的。  
但 `History.recover(id)` 只写“恢复到 state → 触发 render”，没有说明：

- 当前 state 不再引用的图片是否 deref？
- 历史快照中的 imageId 是否要 ref 给当前 state？
- 历史列表本身是否继续持有引用？

这属于模块边界缺口。恢复历史应类似 undo/redo 的引用总账转移：当前 state 占 1 份，历史条目占 1 份，恢复时只改“持有者”，不凭空增减总引用。

---

### 4. 填充布局的“层内比例”模型不足以表达需求

需求 2.3：

> 层内比例：按层分配，每块色-1 个分界线。  
> 例如六色饼图布局下，每层有三色，因此显示三个层内比例，调节饼图单层内三个分界线的角度。

架构 schema 中：

```json
"ratios": [0.5, 0.5]
```

这是一个扁平数组。  
但多层布局下，每层色块数量可能不同，层内比例应**按层分组**，例如：

```json
"ratios": [[0.33, 0.66], [0.25, 0.5, 0.75]]
```

否则无法表达“每层独立的分界线数量与位置”。这是模型结构层面的不足，不是 UI 细节。

---

### 5. 透明色语义边界不清

需求 3.1：

> 透明色选项：勾选后默认白色为透明色导出，注明 JPG 不支持透明。

这是下载模块的“画布背景透明”选项。  
架构中 `canvas.transparent` 的注释却写：

> 语义：白色键控透明（不是“是否填白”）

同时 4.7 又写：

> `canvas.transparent=true` + shape 非 none → 导出时跳过白色填充 + 白色键控透明

这会把“画布背景透明”与“白色像素键控透明”混在一起。  
行图片模式已有独立的 `whiteToTransparent`，不应再由全局透明色选项做全局白色键控，否则可能误伤形状内或内容中的白色。

建议明确：

- `canvas.transparent` 只控制画布背景是否透明。
- `line.whiteToTransparent` 只控制该行图片白色是否透明。
- 两者互不替代。

---

### 6. 参数联动作用域边界需明确

需求 3.7 在“内容参数栏 → 样式模块”下写：

> 所有参数设置，每个参数后面加一个图标表示参数联动。

架构将联动限定为：

```js
LINKABLE_LINE_PARAMS = {
  size, angle, scaleX, scaleY, offsetX, offsetY, clipToShape,
  color.*, shadow.*
}
```

排除了 `fontSize`、`weight`、`italic`、`fontFamily`、`textLayout`。

如果“所有参数设置”仅指样式模块，这没问题。  
但需求原文容易理解为“所有内容相关参数”。建议在架构中明确写：

> V2.02 参数联动仅覆盖内容样式参数，不覆盖文本字体参数和背景参数。

否则实现时容易产生分歧。

---

## 三、内部矛盾

### 1. 新增行 links 继承规则前后矛盾

架构 4.1 JSON 注释：

> 新增行 → 所有可联动参数的 links 全部继承 enabled=true（若全局有任何联动标记）

架构 4.2 `setLineCount` 代码：

> 按参数继承：对每个可联动参数，检查已有行是否有该行 links=true

两者不同：

- 前者：只要全局有任何联动标记，新行所有可联动参数都联动。
- 后者：只继承已勾选的那些参数。

按需求 3.7：

> 如果有参数被勾选联动，新增行也同时联动。

应统一为“按参数继承”，即只继承已有行中 links=true 的参数。

---

### 2. links 键集合不一致

`_lineDef.links` 中没有 `color.gradientType`，  
但 `LINKABLE_LINE_PARAMS` 中包含 `color.gradientType`。

这会导致：

- 行对象上可能没有该 links 键；
- 联动状态机遍历时找不到该键；
- 快照序列化字段不一致。

应统一 links 键集合。

---

### 3. 联动同步依赖 `history` 标志

架构 4.2 `set()` 中，值同步逻辑放在：

```js
if (opts.history) {
  // 同步所有标记了联动的其它行
}
```

但需求要求：

> 调整任意行的大小参数，所有行的大小参数同步变化。

滑块拖动中通常 `history=false`，如果同步逻辑被 `history` 包住，拖动过程中就不会实时联动。  
联动同步应与“是否记录历史”解耦：实时同步值，`mouseup/blur` 时才入栈。

---

### 4. 预设保存路径与引用计数矛盾

如前所述：

- `saveCurrent` 说“等同于 export → push 到 session.presets”；
- `export` 返回含 base64 的 JSON；
- `ImageRepo` 又说 `session.presets[k].imageIds` 计入引用。

如果预设列表存的是含 base64 的 JSON，就不会有 `imageIds` 引用，引用计数模型不成立。  
必须统一为：

> 会话内预设只存 imageId 引用；base64 只在导入/导出交换时出现。

---

### 5. 预览模态双击语义混淆

需求 1.4：

- 模态内双击：复位平移 + 缩放。
- ESC / 关闭按钮：退出模态。

架构 `closeModal()` 注释写：

> ESC / 关闭按钮 / 模态内双击复位 zoom+offset

把“复位”和“关闭”混在一起。  
应明确：模态内双击只复位，不关闭。

---

## 四、需求不匹配 / 遗漏

### 1. 形状默认弧度与需求冲突

需求 1.1.2：

> 默认值：方向和弧度是 0。

架构 schema：

```json
"arc": 22
```

默认弧度 22，与需求“弧度默认 0”不匹配。  
如果圆角方形默认需要圆角，应修改需求或明确说明。

---

### 2. 填充方向旋转中心与需求原文冲突

需求 2.3：

> 旋转的中心点为内容/图片/图标的中心。

架构第十四节写：

> 经确认，旋转中心 = 形状中心（画布中心）（需求原文为笔误）

这是重大需求偏离。  
如果确实要改为形状中心，必须有正式需求变更记录；否则架构应遵循需求原文，或标记为“待确认”。

---

### 3. FA 图标范围与需求“全部图标”可能不匹配

需求 2.7：

> 分类树状展示 FontAwesome6 的全部图标及其形状。

架构确认：

> FontAwesome 6 Free（约 2000+ 图标）。Pro 版本图标不在范围内。

如果需求要求“全部图标”，Free 范围不够。  
需确认产品是否接受仅 Free，以及商用版权合规策略。

---

### 4. 图片上传进度条未在 UI 层落位

需求 2.8：

> 上传图片显示进度条，大于 1MB 时提醒用户会造成卡顿。

架构 `images.upload` 提到 FileReader 和 >1MB 提示，  
但 `ui.js` 中没有明确的上传进度条组件落位。  
这属于需求覆盖遗漏。

---

### 5. 预设导入差异参数的具体展示未落位

需求 2.1：

> 导入预设后显示具体的差异参数情况。  
> 导入完成后显示有参数差异、失败、成功的预设数量及其名称。

架构 `Presets.import` 返回 `{ success, warnings, failures }`，  
但没有说明 UI 如何展示“具体差异参数”。  
建议在 `presets.js` 或 `ui.js` 中补一个差异报告组件。

---

### 6. 原始图片打包的数据来源需明确

需求 3.2：

> 原始图片打包：勾选后，将上传的原始图片一并打包。

架构 `withRawImage` 从 ImageRepo 导出 base64。  
但 ImageRepo 无引用时 5s 延迟释放。  
如果下载时某些图片已无引用，可能无法打包“原始图片”。

建议明确：只要会话内上传过，原始图片是否应保留到会话结束？  
还是仅打包当前仍被引用的图片？这会影响内存模型。

---

## 五、建议修正清单

优先级从高到低：

1. **统一预设存储模型**：会话内预设只存 imageId 引用；交换格式才含剪裁量化 base64。
2. **拆分 `importPreset` / `applyPreset` / `saveCurrent` 职责**，明确图片引用转移。
3. **补全 `history.recover` 的引用转移规则**。
4. **将 `layout.ratios` 改为按层分组结构**，以支持每层独立层内比例。
5. **统一透明色语义**：画布背景透明 vs 行图片白色透明。
6. **统一新增行 links 继承规则**，并统一 links 键集合。
7. **联动同步与 history 标志解耦**，保证拖动中实时同步。
8. **将架构第十四节“经确认”项正式回写需求或标记待确认**，尤其是旋转中心、默认弧度、FA 范围。
9. **明确参数联动作用域**：仅内容样式参数，还是包含字体参数。
10. **补齐 UI 落位**：图片上传进度条、预设导入差异报告。

---

## 结论

架构文档整体方向正确，模块分层和渲染/导出/引用计数的设计思路是成立的。  
但在进入详细设计前，必须先解决以下核心问题：

- 预设、历史、快照、ImageRepo 的引用总账模型；
- 填充布局中层内比例和方向旋转中心的数据模型；
- 透明色语义边界；
- 参数联动作用域与继承规则；
- 架构单方面“确认”与需求原文的冲突。

这些问题不解决，后续实现很容易在图片释放、预设导入导出、撤销重做、多层填充等场景出现难以排查的引用错乱和行为不一致。

# GLM5.3极致
KiconCreator V2 架构文档评审
总评
架构整体骨架扎实：模块划分与需求章节映射清晰，预览层/导出层分离、DPR 隔离、clip 约束、快照不含 base64、UI 视图状态与业务 State 隔离等关键决策正确；“环形向心文本 vs 环形行布局”这类易混概念做了显式区分；歧义确认清单机制本身值得肯定。但存在 3 个 P0 级问题：引用记账自相矛盾、需求明文要求被误读砍掉、预设导入语义前后冲突。以下按严重度列出。
一、P0：内部矛盾（影响功能正确性，必须修订）
1. undo/redo 的图片引用记账三处互斥，按现有文字实现必然出错
同一件事在三处有三种说法：
位置	表述	
4.11 引用场景白名单	“undo/redo 栈间转移 → 转出方栈 -1 + 转入方栈 +1”	
第九节文字	“undo() / redo() 栈间转移不增减 ref”	
第九节伪代码	只出现 derefOnlyIn(currentSnap, previousSnap)（对 current 独有图片 -1）	
分歧核心在“undo 时把当前 state 拍成 currentSnap 推入 redoStack”这一步：
若按“引用从 state 转移给 currentSnap、不 +1”，则 derefOnlyIn 是多余的一次减引用 → current 独有的图片会在 redo 栈中被 5s 延迟释放，redo 恢复时丢图；
若按“新拍快照入栈需 +1”（与 pushUndo 对称），则第九节“转移不增减 ref”的声明和伪代码都漏写了这一步。
在 4.11“refCount = state 1 份 + 每份快照各 1 份”的总账模型下，无论按哪种解读现有文字都配不平账。这正是架构自己风险清单 #1（ref/deref 不对称）预言的事故类型，却在文档内部复现。建议：重写第九节，对每个操作（pushUndo / undo / redo / clearRedo / FIFO 淘汰 / 换图）给出单张图片 refCount 的净变化表，并配套最小单元测试用例。
2. 预设批量导入：4.12 与第十七节互相矛盾，且与需求不符
需求 2.1：“导入完成后显示有参数差异、失败、成功的预设数量及其名称” → 部分成功是预期行为；
4.12 import() 返回 { success[], warnings[], failures[] } → 逐条评估，支持部分成功；
第十七节：“原子替换：全部成功才入列” → 全或无，“成功数量”恒为 0 或 N。
三处无法同时成立。建议明确为“单条事务原子、批量允许部分成功”，失败条目不入列但出现在报告中。
3. 背景边界参数的“联动”被单方面砍掉，砍掉依据与需求原文不符
需求（三）2.3 原文：“参数有滑块、参数值显示兼输入框、联动、重置等按钮”——“联动”白纸黑字在列；
架构 4.2 强约束“boundary / shape / layout 对象没有 links 字段”，并辩称“需求三 2.3 有‘重置’能力但未要求联动链条 UI”——同一句列表中“重置”与“联动”并列，不可能只见其一。
客观地说，联动机制定义在跨行参数之间，对全局唯一的 boundary 参数可能确实无意义（很可能是需求复制通用控件描述所致），但正确做法是进歧义清单请需求方裁定，而不是宣称需求没写并直接砍掉。
二、P1：需求不匹配 / 超范围扩展
4. 行颜色渐变参数超出需求范围，并直接造成联动系统数据结构不一致
需求 3.4 行颜色只有“单色/渐变 + 选择器 + 颜色建议”，渐变类型（线性/径向）与渐变角度只定义在背景渐变（3.2.2）。架构给 _lineDef.color 加了 gradientType / gradientAngle，属于超范围扩展——而架构 4.2 自己引用“豆包评审 P0#2：超范围设计会引入多余字段”来限制背景联动，却在行颜色上做了同类扩展，双重标准。直接后果：color.gradientType 进入了 LINKABLE_LINE_PARAMS，但 _lineDef.links 中没有这个键，toggleLink 将写入 undefined 键，联动图标无数据来源。
5. 弧度默认值违背需求
需求（三）1.1.2 明确“默认值：方向和弧度是 0”；架构 shape.arc 默认 22，且 schema 约束表未收录 arc。
6. canvas.transparent 存在双重语义，schema 注释与 render 流水线互相否定
schema 注释：“白色键控透明（不是‘是否填白’）”；
render 2a：shape=none 且 transparent=true → “跳过白色填充”——这就是“是否填白”。
需求 3.1（白色为透明色导出）与 1.8（形状为无时按白/透明导出）实际要求该开关同时承担两个效果，可以统一，但文档必须写清统一语义。此外它与行级“图片白色转透明”（需求 2.8）的叠加关系（全局键控 vs 行级预转换的先后）完全未提及。
三、P1：文档内部不一致（会被实现放大）
7. 模块依赖图与正文矛盾，缺 3 条边
export.js 复用 Presets.export（toJSON）且 toHTML 与 copyHTML 同一实现 → 缺 export→presets；
presets.renderList 缩略图“走 render” → 缺 presets→render；
history.record 缩略图同样“render → toBlob” → 缺 history→render。
依赖图是模块边界的权威表达，普通 <script> 按序加载策略下，缺边会让加载顺序问题推迟到实现期才暴露。
8. layerOrder 枚举命名与需求选项名方向相反，未给映射表
需求选项「1行->9行」= 绘制顺序 9→1（行 1 最顶层）；架构枚举 9-to-1 描述的恰好是同一状态，但命名方向相反。UI 显示需求文案、state 存架构枚举，无显式映射极易接反，且单行场景下不易发现。
9. FA 命名两处矛盾：4.8 makeName 写“unicode 或 iconName”；十四节歧义确认“= iconName，不是 unicode”。
10. 行对象初始化模型二义：schema 说“9 个完整 line 对象无论 lineCount 都常驻”，setLineCount 又处理“从未被初始化过的行”（__initialized 懒初始化），两者不能同时成立；且 __initialized 是否入快照未定义。
11. whiteToTransparent 归属路径不一致：_lineDef 中是行级顶层字段，4.11 引用清单却写 content.lines[i].image.whiteToTransparent。
四、需求覆盖缺口
层内比例模型分歧：需求例子“四色矩阵 2 层显示一个层内比例”（暗示各层分界线共享比例）；架构按“每层独立分界线”设计（该例为 2 条），滑块数量不同，需确认。
响应式缺口：手机横屏恢复三栏（需求 2.6）、竖屏预览最大高度 ≤ 视口 1/3（需求 1.2）、默认基准视口 800×400（需求 2.2）均未落入响应式设计。
排版缺口：5 行“四宫格+中央”不属于 rows×cols 模型，layouts.js 的 grid/multi 注释均未承接。
canvas 导出方案空缺：需求要求“<canvas> 标签+内联脚本”；架构 toCanvas 只有 DPI=1 空壳示例。内联脚本意味着需自包含的 state 序列化 + 绘制逻辑打包，这是影响 render.js 是否保持可序列化的架构级决策，不是细节。
小缺口合并：图片上传进度条（需求 2.8）未入 images.js 接口；图片/FA 模式下“上传/图标”标签落位于样式模块（需求 2.3）未明确；“字体加载完成后再开始渲染”（需求 2.6）被改为“先渲染占位+提示”——方案更优但属行为变更，应走歧义确认而非静默修改。
五、P2：模块边界与组织建议
引用计数规则散布四处（4.2 / 4.11 / 第六节 / 第九节），且如问题 1 所示已互相打架。应收敛到 ImageRepo 单一章节作为唯一权威；顺带评估把 ImageRepo 从 state.js 拆出——目前 state.js 五合一（状态 + undo/redo + 联动状态机 + 行管理 + 仓库），是全工程被依赖最重的模块。
事件机制无归属：state:changed、colors:*Changed、links:changed、字体加载提示等 emit/on 散布各模块，但没有任何模块承载事件总线（utils.js 职责清单也没有）。render“触发 preview 层字体提示”这类跨层副作用应统一走事件。
颜色建议的双向基准区分正确（值得肯定），但多色/多行时基准取值不完整：文本侧写了“取第一个”，背景 1~6 色取哪个色块作为内容颜色建议基准未定义。
六、建议补充进“需求歧义与确认”清单
现有 7 条质量不错，建议补入：① 边界参数“联动”是否有意义（问题 3）；② 层内比例共享 vs 独立（问题 12）；③ transparent 统一语义及与行级白转透的关系（问题 6）；④ 行渐变是否需要类型/角度（问题 4）；⑤ canvas.size 非单调截断（10000 合法但 10001→8192，确认是否本意上限 8192）；⑥ clipToShape 默认值——需求参数名“显示超出形状范围的内容”与架构字段语义相反；⑦ 行布局 ring 半径 canvasSize/4 为架构自定；⑧ 内容参数栏标题“两个模块”vs 正文三模块。
结论
架构的数据模型、分层与大多数需求映射是扎实的，歧义确认机制是好实践。但 P0 三项暴露出两个关键失守点：引用记账这一架构最需要自律的规则自身无法配平，以及以失实的“需求没写”为由单方面收缩范围。建议：先修订 P0/P1（重写第九节并配净变化表、统一预设导入语义、重新裁定联动范围）、重画依赖图、补齐歧义清单，之后再进入详细设计与验收测例制定。

## 二、模块边界评审（各js文件职责划分）
### ✅ 合理划分
1. **shapes.js：只输出点集、Path2D，不做绘制**，输入配置输出points/path/boundingBox；绘制交给render.js。边界清晰。
2. **layouts.js：仅处理多行内容行的排布，输出每行的位置、旋转，不碰文本/图片绘制**；环形行布局与字符向心文本分离。
3. **fillers.js：分割形状为色块块、边界曲线生成、过渡颜色混合；不直接操作canvas绘制**，输出clipPath、block信息，交给render做实际渲染。职责边界清晰。
4. **render.js：纯渲染引擎，只接收state+canvas，区分`mode:'export'`/预览渲染；严格隔离预览层元素（辅助线、灰白格子），预览元素全部由preview.js的DOM层实现，render导出路径完全不绘制。**
5. **state.js：只负责状态、快照栈、ImageRepo、参数联动；不操作DOM、不渲染。**
6. **ui.js：只负责DOM组件构建、响应式布局、参数控件；不执行业务逻辑计算，通过路径回调调用state.set()。**
7. **preview.js：完全UI视图层，维护zoom、offset、模态、辅助线、安全边距，**不修改业务state**。
8. **export.js：复用render的export模式，生成临时1:1 canvas；多格式、命名、ICO二进制、ZIP打包集中在此。**
9. **presets.js：导入导出、缩略图生成；缩略图异步不阻塞主界面。**
10. **history.js：下载历史记录，复用快照模型；不混入业务渲染。**
11. **images.js：上传、剪裁、whiteToTransparent；引用计数只调用state.ImageRepo，不直接修改state对象。**
12. **fonts.js：字体加载、文本、FA绘制；fa_map.js纯静态数据，不包含业务逻辑。**

### ⚠️ 模块边界风险点
1. **state.js中参数联动逻辑与UI的分离**
    - `toggleLink`、`batchSet`全部放在state.js；UI（ui.js）只调用接口，不实现联动业务逻辑。**架构设计正确：联动是业务状态规则，不是UI表现。**
    - 注意：禁止在ui.js内部修改`lines[].links`，全部走`State.toggleLink()`接口。架构文档已经写明接口。

2. **边界曲线（boundary）归属 fillers.js**
    - 需求：边界属于布局级别，不是每个fill独立配置；架构中`background.boundary`挂在background下，不是fill子对象；计算逻辑在fillers.js。**模块归属正确。**

3. **ICO二进制实现在export.js**
    - 手写二进制，不依赖外部ICO库，符合需求；模块归属正确。

4. **颜色建议逻辑在colors.js**
    - 两套入口：`suggestContentColors()`（背景→内容颜色建议）、`suggestFillColors()`（内容→填充颜色建议）；事件驱动，UI仅展示候选项，不直接修改参数（一键纯色填充除外）。

1. **ImageRepo放在state.js内部**
    > 现状：ImageRepo作为`State.ImageRepo`，属于state.js模块。
    - 优点：方便undo/redo快照做ref/deref；
    - 缺点：图片上传、剪裁逻辑在`images.js`，图片资源管理放在state，跨模块耦合。

2. **fa_map.js：静态数据，无业务逻辑**
    - 架构补充`category`、`pathData`，支持Path2D绘制FA图标，避免依赖DOM字体渲染，符合需求；归属正确。

### 需求原文‑参数联动规则（二‑(二)‑3.7）
> 开启任意参数的联动，则启用全部行该参数联动，其它所有行该参数联动同步被启用。调整任意行，所有勾选联动的行同步变化；取消仅取消当前行；新增行继承联动；行隐藏保留联动标记。

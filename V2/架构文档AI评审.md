# deepseek

总体结论：**架构方向基本正确，覆盖度较高，但还不能作为可开发基线。**  
它已经抓住了几个关键架构点：模块拆分、状态管理、图片仓库引用计数、撤销重做、预览/导出分离、下载组合矩阵、参数联动两阶段状态机。但文档定位有些混杂：一方面写了大量伪代码、字段、算法，接近详细设计；另一方面真正架构层面需要的**模块契约、数据流、状态边界、错误降级、验收映射**又不够系统。更重要的是，存在若干与需求直接冲突或明显遗漏的点，建议先修 P0，再有条件通过。

---

## 一、作为架构文档的定位评价

优点：

- 目录结构、文件依赖图清晰，能看出各模块职责。
- `preview` 与 `export` 的差异清单很好，直接对应“辅助线/棋盘格不导出”。
- 下载组合矩阵、命名规则、ICO 格式说明较完整。
- `ImageRepo` 引用计数、undo/redo 快照、redo 清空时 deref 的设计方向正确。
- 参数联动“两阶段状态机”比常见实现更贴近需求。
- 对部分需求歧义做了标注，例如填充方向旋转中心、边界参数范围。

问题：

- 架构文档中混入大量详细设计：伪代码、字段默认值、CSS 变量、实施阶段。这些不是不能有，但应拆分到详细设计，架构层应保留**决策、边界、接口、状态、数据流、非功能约束**。
- 缺少正式的架构视图：运行时视图、事件流、错误处理、降级策略、性能预算、可测试性、验收映射。
- 多个需求点只在实施阶段列了待办，没有在架构中定义清楚边界和契约。

---

## 二、覆盖较好的部分

- 产品定位：纯浏览器、无后端、无 localStorage，架构选型一致。
- 预览：原位缩放、模态、辅助线、安全边距、棋盘格不导出，基本覆盖。
- 下载：PNG/JPG/WebP/ICO/Canvas/JSON/HTML/ZIP 组合矩阵清楚。
- 预设与历史：内置预设、导入导出、缩略图 ≤50px、历史 20 条、imageId 引用，方向正确。
- 内容与样式：文本/图片/FA、尺寸/颜色/阴影、联动、复制样式，数据模型基本覆盖。
- 背景：形状、填充数量、矩阵/饼图、边界、色块独立模式，覆盖较全。
- 主题与响应式：三主题、级联压缩原则、标签组唯一/并行，有架构意识。

## 三、必须修正的 P0 问题

| 问题 | 需求依据 | 架构表现 | 建议 |
|---|---|---|---|
| 图片引用规则冲突 | 需求 2.8：更换图片解除旧引用；**切换行和模式不解除引用** | 架构 `images.js` 写“切换 mode 解除旧 mode 引用” | 修正为：引用只随 `imageId` 变更、行删除、快照淘汰、预设/历史删除而增减；模式切换保留 `imageId` 引用 |
| 参数联动范围不足 | 需求三 2.3：边界参数 `A/ω/φ/k` 有联动、重置 | 架构 `links` 只挂在 `content.lines`，背景边界无联动定义 | 抽象通用“可联动参数注册表”，支持 `background.boundary.params.*` 等非行参数 |
| 颜色建议基准混淆 | 需求 3.4：内容颜色建议基于背景色；需求三 2.4：填充颜色建议基于文本颜色 | 架构 `colors.suggestions(baseColor)` 注释与事件只提背景色变更 | 拆成两个独立建议入口：内容建议依赖背景填充色；填充建议依赖文本颜色，并各自定义触发事件 |
| `canvas.size` 校验不一致 | 需求 3.2：输入 <0→16，>10000→8192 | 架构 SCHEMA 写 16~8192，会提前截断 8193~10000 | 明确合法区间为 16~10000，>10000→8192，或与产品确认 |
| HTML 下载与复制未区分 | 需求 2.1 复制 HTML 到剪贴板；需求 3.3 下载格式含 HTML | 架构 `toHTML` 与 `copyHTML` 同一实现 | 区分“复制到剪贴板”和“生成 .html 文件下载”，接口参数化 |
| FA 图标范围不一致 | 需求：FontAwesome6 全部图标 | 架构选型为 FontAwesome 6 Free | 确认是否只支持 Free；若“全部”包含 Pro，授权与数据包都需重新评估 |
| 边框“向外延伸”未定义 | 需求 1.2：边框从形状边框向外延伸 | Canvas `stroke` 默认线宽居中，一半内一半外 | 架构需明确：路径外扩、线宽偏移，还是接受视觉近似 |
| 预设导入/导出图片迁移不完整 | 需求 2.1、性能优化 1 | 架构有剪裁量化，但批量导入失败回滚、重复 imageId、ref 迁移未定义 | 定义导入事务：先解析、校验、注册图片、再替换预设；失败不破坏现有仓库 |

## 四、重要遗漏或不清晰点（P1）

- 竖屏预览“固定浮动、最大高度不超过视口 1/3”未在架构中明确。
- 响应式断点缺失：800×400、三栏→中右合并→单栏、手机横排三栏，目前只有原则，没有可验收状态机。
- 标签组“平分法拆解”只有概念，没有算法边界和激活状态保持规则。
- 上传图片进度条、>1MB 提醒、上传失败原因提示未体现。
- 快捷键未明确“输入框/textarea 聚焦时交给浏览器原生撤销”。
- 撤销栈“根据设备动态降低上限”未体现。
- 快照边界未定义：历史/撤销快照是否包含 `session.presets`、`session.history`，避免循环引用。
- 顶部工具栏缺少作者 `Kong`。
- 填充层间/层内比例的多滑块共享滑轨、均分按钮、方向多滑块，UI 契约不足。
- 边界参数联动、重置未定义。
- 预览“形状非无时标签显示形状”未明确。
- SVG 未来扩展只提“不支持”，未预留架构边界。
- 需求技术开发流程要求“验收测例、参数合法校验公式、JSON schema”，架构只有阶段验收，缺少功能点测例矩阵。

---

## 五、需要产品确认的歧义

1. 填充方向旋转中心：需求原文写“内容/图片/图标中心”，架构自行确认为“形状中心”。必须回写需求并签字。
2. 边界参数 `A/ω/φ/k` 的合法范围：架构暂定 `A∈[-0.5,0.5]`、`ω∈[0.01,10]`，需确认。
3. FA 是 Free 还是包含 Pro 的“全部”。
4. HTML 下载格式到底是下载 `.html` 文件，还是仅复制 `<link>` 文本。
5. `canvas.size` 在 8193~10000 是否合法。
6. 命名规则中“总长度截断”具体截到多少，架构暂定 30 字符。
7. 历史/撤销快照是否只保存业务状态，不保存 `session.presets/history`。

## 六、建议补充的架构内容

不是要求写详细公式，而是架构层应补：

- 模块接口契约：`State`、`Renderer`、`ImageRepo`、`Export`、`Presets` 的输入输出和错误码。
- 事件总线：`state:changed`、`links:changed`、`colors:changed`、`image:added/released`、`font:loaded/failed`。
- 快照 Schema：明确哪些字段进入 undo/history/preset，哪些不进入。
- 响应式状态机：断点、栏合并、预览固定、标签组展开/折叠、反压滚动。
- 图片仓库生命周期图：上传、引用、切换模式、切换行、快照淘汰、预设导入、历史删除。
- 错误与降级：字体失败、图片失败、WebP 不支持、剪贴板失败、CDN 失败。
- 验收矩阵：需求功能点 → 架构模块 → 验收测例。
- 演进预留：SVG、矢量图、更多主题、更多下载格式。

---

## 结论

**建议状态：有条件通过。**  
架构文档的骨架和方向是对的，尤其预览/导出分离、下载矩阵、图片仓库、联动状态机是亮点。但它目前更像“架构 + 详细设计 + 实施计划”的混合体，且存在几个与需求直接冲突的 P0 问题。先修正图片引用规则、参数联动范围、颜色建议基准、尺寸校验、HTML 下载语义、FA 范围、边框外延、预设图片迁移，再补齐响应式、快照边界和验收矩阵，才能作为 V2.02 的开发基线。

二、P0：需求映射错误与内部矛盾（必须修订）
2.1 JSON 导出与预设导出自相矛盾（需求 3.3）
需求 3.3 明确：json 格式"等于导出预设"；而需求 2.1 规定预设导出"连同图片数据一同导出，剪裁量化，只保存可见部分"。
架构中 Export.toJSON() 写的是"JSON.stringify(state, 剥离 imageId 的 base64)"，而 Presets.export() 是剪裁量化保存图片数据。两者不一致。
后果：按 toJSON 的设计，导出的 json 重新导入后所有图片都变成"图片缺失"占位，违背需求。
修订建议：toJSON 应复用 presets.export 的剪裁量化路径，二者统一为同一函数。
2.2 图片仓库的归属与快照序列化边界矛盾（内存设计缺陷）
第 6 节 ImageRepo.store 是独立 Map；但第 4.1 节 schema 根对象里又有 "session": { "images": { "img_xxx": { "data": "<base64>", ... } } }——base64 被放进了 state。
第 4.2 节撤销栈定义"快照 = JSON.parse(JSON.stringify(state))"，同时注释"imageId 保留字符串引用（不复制 base64）"——若 state 含 session.images.data，这行注释不成立：20 条快照 × 数 MB base64 = 内存灾难。
修订建议：明确"可快照 state（canvas/content/background/theme/version）"与"运行时资源（ImageRepo、session 列表）"两个集合的边界，快照仅序列化前者；schema 中的 session 结构应标注"仅示意存储语义，不参与快照序列化"，或直接从 state JSON 中移出。
2.3 lines"常驻 9 个 + enabled 控制"与 addLine/push 示例矛盾
第 4.1 节 schema 注释："9 个完整 line 对象（无论 lineCount 多少都常驻），显示由 enabled 控制"——这是满足需求 3.3"行被减去增加后其参数和模式不必重置"的唯一正确设计。
但第 4.2 节 addLine() 示例代码是 state.content.lines.push(newLine)——push 新 DEFAULT_LINE 意味着减行再增行会丢失原参数，与需求直接冲突，也与本架构自己的 schema 注释和第 8 节（"该行被移除，但在 lines 数组中保留对象 enabled=false"）冲突。
修订建议：删除 addLine/push 示例，统一为"lineCount 切换 = 修改 enabled 标记"；行数 1~9 固定数组。
2.4 canvas.size 校验规则矛盾
需求 3.2：<0 → 16，>10000 → 8192，默认 256。
架构约束表写"16~8192，<0→16, >10000→8192"。两条规则在 (8192, 10000] 区间冲突（如输入 9999：按需求合法，按范围表被截断为 8192），且 10000 本身归属未定义。
修订建议：按需求语义定义分段函数（<0→16；>10000→8192；其余取 clamp(值, 16, 10000) 或与需求方确认 8192 上限的意图），并在约束表中消除二义性。
三、P1：需求点缺失（需补入架构）
#	缺失点	需求出处	说明	
1	file:// 加载策略未定义	产品定位"零安装、全程序在浏览器运行"	目录含 16 个 JS 文件，但技术选型又写"原生 ES6+ 单文件零依赖"。若用 ES modules，file:// 协议下因 CORS 直接不可用，双击 index.html 的核心场景就废了。必须明确：普通 <script> 顺序加载，或构建为单 HTML 产物。这是整个技术选型的地基问题。

8	颜色建议的双向基准未区分	二.3.4 vs 二.2.4	需求明确：行颜色建议的基准是"当前背景色"，背景填充颜色建议的基准是"文本颜色"。colors.suggestions(baseColor) 接口支持，但两个调用方向的接线未写明，易做反。	
9	arrangement 完整枚举缺失	一.2.2	schema 注释"见 layouts.js 完整枚举"，但 layouts.js 一节并未给出 1~9 行全部排版模式的枚举表。这是 schema 的核心字段，应在架构层闭环。	
10	验收测例未制定	四.技术开发流程	需求明确要求"针对各功能点制定开发验收测例"，架构仅有每阶段一句验收描述，不满足该交付要求。	
四、P2：建议补充/澄清
html 下载格式交互歧义（需求 3.3）：需求字面是"直接复制一整套 link 标签"，即点击后是复制到剪贴板而非下载 .html 文件？与"点击即下载对应格式的文件"存在需求内部矛盾，建议补入第 14 节歧义清单。
快照范围与入栈条件：schema 根含 session.presets/history，若全量快照含它们，则下载历史入列、预设保存是否触发 undo 入栈？需明确快照 schema 仅含绘图数据。
事件总线归属：全文多处 emit('state:changed') / colors:changed，但没有任何模块负责定义 pub/sub 基础设施，应明确落在 utils.js 或独立的 bus.js。
命名截断长度 30 字符：需求只说"做总长度截断"，30 是架构自定值，应标注"暂定，待确认"。
schema 约束表不全：fontSize、阴影 size/blur/offset、形状 size/arc、图片 size/offset 等均未列范围，需求要求"对各参数制定合法校验公式、上下限"，至少应给出完整性承诺和补全计划。
字体列表示例错误：Noto Sans SC 与 思源黑体 是同一字体的两个名字，并列展示会误导；另需注明 web 字体的 CDN 来源与离线回退链。
上传进度条：需求 2.8 要求"上传图片显示进度条"，images.js 未提（FileReader 有 onprogress，可行）。
快速复制/粘贴样式按钮：需求 2.9 明确"内容标签的标签内容最顶上有两个按钮"，ui.js 组件清单中未落位（仅阶段计划出现）。
失效图片引用的主画布降级：预设"图片缺失"占位只定义了缩略图场景；主画布渲染遇无效 imageId 的行为（画占位/跳过/报错）未定义。
模块折叠：需求三 2.1"压缩、折叠和大小调整"，响应式设计只覆盖压缩与合并。

### 2.4 架构层面风险点（架构文档应显性标记风险，传递给开发）
> 下面这些是业务本身固有的风险，应当在架构文档开辟「架构风险与注意事项」章节，当前分散埋在各个注释中，没有汇总。

1. **内存风险：图片仓库引用计数正确性**
> 风险来源：多处来源（undo、redo、history、presets、lines、fills）都对imageId增减引用，任何一处ref/deref漏写，会发生两种问题：内存泄露图片无法释放 / 还在使用的图片被错误释放。
> 架构文档应当在架构层面显式标记风险点：所有修改图片引用的位置必须成对调用ref/deref，定义检查清单。

2. **Canvas clip 累积状态风险**
文档提到`clip必须包裹save/restore`，但应当作为顶层风险提示：所有clip操作，无论渲染预览还是导出，强制遵循save‑clip‑restore范式，禁止全局持久clip，一旦违反会造成渲染错乱。

3. **边界曲线数学计算崩溃风险（sin/tan）**
需求要求：防止除零、无穷大导致渲染崩溃，渲染做截断保护，超出画布大小10倍后截断。
> 当前文档分散写在fillers.js注释，架构层汇总风险：边界参数来自用户输入，用户可通过UI滑块/输入框输入，必须两层保护：schema参数范围校验 + render渲染阶段二次截断兜底，两层防护缺一不可。

4. **撤销重做快照体积风险**
> 快照是全量JSON快照，上限20条。虽然图片只存imageId，但是state对象本身很大（lines[9], fills[6]嵌套多层对象），低端浏览器大量操作会造成内存压力。
> 需求提到撤销栈“根据设备动态降低上限”，架构文档只写固定20，没有写明动态降级策略的触发条件（架构应当提示风险：后续详细设计需要定义降级规则）。

5. **预设导出时图片剪裁量化风险**
> presets导出时，对图片做“剪裁量化，仅导出可见部分图片数据”。风险：当用户导入预设后，原始完整图片丢失，只能拿到裁剪后片段。架构文档需要写明业务契约：导出预设JSON里面图片是裁剪后的片段，**预设导入后会把base64注册进图片仓库**。

6. **Web字体加载异步带来的竞态风险**
字体异步加载，渲染线程和字体加载完成不同步，架构已设计“字体加载中”占位。架构风险提示：UI、渲染线程必须处理三种状态：未加载、加载中、加载失败回退，防止渲染错乱。

7. **响应式UI复杂状态风险**
标签组自动拆分、并行/唯一标签组、级联压缩链路，逻辑复杂；手机横/竖屏切换时会重新布局，容易出现标签激活状态丢失。架构文档应标记风险：响应式重布局**不得修改业务state数据，只修改DOM视图；标签激活状态必须独立维护，不因重布局丢失**。
